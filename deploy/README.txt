Compoza — изолированный пилот

Приложение и API обслуживаются с одного HTTPS-адреса, cookies HttpOnly/Secure,
SameSite=Lax. GitHub Pages — только точка входа; база и пароли туда не попадают.

Контейнер compoza-core, каталог /opt/compoza, порт 127.0.0.1:18190,
общая только сеть HTTPS-шлюза projects-shared-proxy. Чужие БД и контейнеры
не используются. Память 256 МБ, CPU 0.5, один worker, SQLite для пилота.

Перед запуском сверить IP шлюза с --forwarded-allow-ips в Dockerfile.
Текущий доверенный proxy: 172.19.0.5; произвольные X-Forwarded-For не доверять.
COMPOZA_ORIGINS должен совпадать с HTTPS origin приложения.

Резерв: deploy/backup.sh; ночной запуск через отдельный cron compoza-backup.
Копии на том же VPS не заменяют внешний резерв. Перед сдачей копия переносится
в игнорируемую .private/ и проверяется локально. Последующую внешнюю регулярную
доставку резерва нужно закрепить отдельным операционным регламентом.

Пилот использует учебные объекты. Реальные данные импортируются после проверки
прав доступа и согласования актуального источника. SQLite не является обещанием
работы нескольких серверов; переход к PostgreSQL планируется до горизонтального
масштабирования и подтверждается отдельной миграцией/тестом восстановления.

Нативные приложения, финансовые расчеты, полноценные закупки, загрузка файлов
и интеграции следующих этапов не считаются выполненными этим пилотом.

Резервные копии (schema 4)
-------------------------
Фотографии хранятся рядом с базой в data/uploads, вне статического приложения.
COMPOZA_UPLOADS может переопределить этот путь; backup.sh должен использовать тот же каталог.
Штатный backup.sh создает закрытый full-<UTC>.tar.gz: согласованную копию SQLite,
все фотографии, на которые ссылается эта копия, и манифест SHA-256.
Каждый архив проверяется полной распаковкой, integrity_check, foreign_key_check,
сверкой всех 17 таблиц и хешей/размеров каждого фото. Хранение — 14 дней.
Копии содержат учетные секреты: доступ только администратору сервера.
Автоматический внешний резерв пока не настроен. После каждого выпуска сохраняется
дополнительная проверенная копия вне VPS; для постоянного внешнего резерва нужен
отдельный закрытый пункт хранения и проверка оповещений об ошибках.

Проверка архива без переключения сервиса:
  python -m core.archive verify /backups/full-<UTC>.tar.gz

Восстановление выполняется только после проверки архива и остановки записи.
Сначала сохранить текущее состояние и время последней записи. В отдельный закрытый
каталог восстановить core.sqlite3 и uploads из проверенного архива, выставить
владельца 10001:10001, базу/фото 0600 и каталог фото 0700. Проверить версию схемы
и запустить соответствующий выпуск приложения на восстановленной копии.
Проверить вход, роли, задачи, историю сдач и открытие фотографий до переключения.
Не накатывать старую базу поверх новых данных работающей системы.
Откат на schema 3 требует совместимого снимка базы: старый образ schema 4 не читает.

Ограничение объема фотографий по умолчанию — 1 ГБ; COMPOZA_PHOTO_STORAGE_BYTES
позволяет увеличить его после проверки места под резервные копии. При остатке
диска менее 1 ГБ загрузка приостанавливается. Непривязанные файлы удаленных
черновиков удаляются через 14 дней, только после успешного полного резервирования.
